LeakGuard 분산 통신 시스템 설계안
=================================

문서 버전: 1.0
작성일: 2026-07-27
대상 시스템: Raspberry Pi 서버 - Jetson Nano 클라이언트 - STM32 클라이언트


1. 핵심 결론
------------

NDJSON(Newline-Delimited JSON)은 프로그래밍 언어가 아니라 통신 메시지 형식이다.
Node.js를 사용해야 한다는 의미도 아니다.

현재 프로젝트에 가장 적합한 언어와 메시지 형식은 다음과 같다.

장치             권장 언어       메시지 형식
Jetson Nano      Python 3        NDJSON
Raspberry Pi     Python 3        NDJSON 수신 및 ASCII 변환
STM32            C              기존 ASCII/CSV 파서 유지

권장 통신 구조:

Jetson Nano -- TCP/NDJSON --> Raspberry Pi -- TCP/ASCII --> STM32
Jetson Nano <-- TCP/NDJSON --- Raspberry Pi <-- TCP/ASCII -- STM32

Raspberry Pi는 두 프로토콜 사이의 변환기이자 중앙 서버로 동작한다.
STM32에서 이미 개발 중인 ASCII 기반 C 파서는 변경하지 않는 것을 권장한다.


2. NDJSON이란 무엇인가
---------------------

NDJSON은 JSON 객체 하나를 한 줄에 하나씩 기록하고 줄바꿈 문자로 메시지를
구분하는 형식이다.

예:

{"v":1,"type":"status","device_id":"jetson-01","seq":152,"level":"WARNING"}\n
{"v":1,"type":"heartbeat","device_id":"jetson-01","seq":153}\n

여기서 "\n"은 메시지 종료를 의미한다.

NDJSON을 사용할 수 있는 언어에는 제한이 없다.

- Python: json.dumps(), json.loads()
- C: cJSON, JSMN 등의 라이브러리
- C++: nlohmann/json
- JavaScript/Node.js: JSON.stringify(), JSON.parse()
- Java: Jackson, Gson

본 프로젝트에서는 Jetson Nano와 Raspberry Pi가 이미 Python 환경을 사용하기
때문에 Python을 사용하는 것이 구현과 유지보수 측면에서 가장 단순하다.


3. 화면 문자열을 다시 파싱하면 안 되는 이유
----------------------------------------

Jetson Nano의 화면에는 다음처럼 사람이 읽기 위한 문자열이 표시된다.

Leak area: 2.364%
LEVEL: WARNING
Spreading: NO

이 화면 문자열을 다시 읽고 분리해서 네트워크로 보내면 안 된다. 화면의 문구,
공백 또는 소수점 표시가 바뀌면 통신이 깨질 수 있기 때문이다.

현재 Jetson 코드에는 이미 구조화된 LeakStatus 객체가 있다.

LeakStatus(
    detected=True,
    leak_ratio=2.364,
    spreading=False,
    danger_overlap=False,
    level="WARNING"
)

올바른 처리:

LeakStatus 객체
  -> NDJSON 메시지로 직렬화
  -> Raspberry Pi로 전송
  -> Raspberry Pi가 JSON 객체로 역직렬화
  -> STM32용 ASCII 메시지로 변환


4. 장치별 책임
-------------

4.1 Jetson Nano

- 카메라 입력
- U-Net 추론
- 이진 마스크 후처리
- 누수 면적 계산
- 확산 여부 계산
- Danger ROI 침범 계산
- NORMAL/SMALL_LEAK/WARNING/DANGER 단계 결정
- LeakStatus를 NDJSON으로 직렬화
- Raspberry Pi에 5~10Hz로 최신 상태 전송
- 단계 변경 또는 DANGER 발생 시 즉시 전송
- 네트워크가 끊겨도 추론 계속 수행
- Raspberry Pi에 자동 재접속

4.2 Raspberry Pi

- TCP 서버
- Jetson Nano와 STM32 연결 수락
- HELLO 메시지로 장치 역할 및 ID 확인
- Jetson NDJSON 메시지 파싱 및 검증
- 최신 Jetson 상태 저장
- Jetson 상태를 STM32용 ASCII 패킷으로 변환
- STM32 상태 수신 및 저장
- 이벤트 및 통신 상태 로그
- 향후 웹 대시보드와 원격 명령 제공
- 클라이언트 연결 해제 및 재접속 처리

4.3 STM32

- TCP 클라이언트
- Raspberry Pi가 보낸 ASCII 패킷 파싱
- 누수 상태를 로컬 FSM 입력으로 사용
- LED, 부저, 팬, 펌프, 밸브 제어
- 패킷 범위와 형식 검증
- 통신 타임아웃 감지
- 통신 장애 시 Fail-safe 수행
- DANGER 상태 latch
- 안전한 RESET 조건 판단


5. 권장 Jetson -> Raspberry Pi 메시지
------------------------------------

5.1 연결 등록

{"v":1,"type":"hello","role":"jetson","device_id":"jetson-01","software":"leakguard","software_version":"1.0"}\n

5.2 누수 상태

{"v":1,"type":"status","device_id":"jetson-01","seq":152,"timestamp":1721800000.250,"detected":true,"leak_ratio":2.364,"instant_ratio":2.401,"spreading":false,"spreading_delta":0.031,"danger_overlap":false,"danger_overlap_pixels":0,"level":"WARNING","leak_pixels":4085,"inference_ms":24.8,"fps":18.5}\n

필수 필드:

- v: 프로토콜 버전
- type: 메시지 종류
- device_id: 장치 고유 ID
- seq: 순서 번호
- timestamp: 생성 시각
- detected: 누수 확정 여부
- leak_ratio: 이동평균 누수 면적 비율(%)
- spreading: 확산 여부
- danger_overlap: Danger ROI 침범 여부
- level: 4단계 누수 상태

진단용 권장 필드:

- instant_ratio
- spreading_delta
- danger_overlap_pixels
- leak_pixels
- inference_ms
- fps

5.3 Heartbeat

{"v":1,"type":"heartbeat","device_id":"jetson-01","seq":153,"uptime_ms":843920}\n

Heartbeat 권장 주기: 1초


6. 권장 Raspberry Pi -> STM32 ASCII 메시지
-----------------------------------------

STM32의 기존 ASCII 기반 C 파서를 유지하기 위해 Raspberry Pi가 다음처럼
변환한다.

LEAK,<seq>,<detected>,<ratio>,<spreading>,<danger>,<level>\n

예:

LEAK,152,1,2.364,0,0,WARNING\n

필드:

LEAK       메시지 종류
152        Jetson 상태 순서 번호
1          누수 확정
2.364      Monitoring ROI 대비 누수 면적(%)
0          확산 아님
0          Danger ROI 미침범
WARNING    현재 단계

Raspberry Pi Heartbeat:

HEARTBEAT,981,1721800000\n

중요 명령:

CMD,381,RESET\n
CMD,382,MODE,AUTO\n
CMD,383,MODE,MANUAL\n

STM32 응답:

ACK,381,RESET,OK\n
ACK,382,MODE,AUTO,OK\n
STATE,stm32-01,AUTO,DRYING,80,0,0\n


7. Raspberry Pi 변환 예시
------------------------

Jetson NDJSON 수신:

message = json.loads(line)

STM32 ASCII 변환:

packet = (
    f"LEAK,{message['seq']},"
    f"{int(message['detected'])},"
    f"{message['leak_ratio']:.3f},"
    f"{int(message['spreading'])},"
    f"{int(message['danger_overlap'])},"
    f"{message['level']}\n"
)

Raspberry Pi는 다음 항목을 확인한 뒤에만 STM32로 전달해야 한다.

- v가 지원하는 프로토콜 버전인지
- type이 허용된 메시지인지
- device_id가 등록된 장치인지
- seq가 정수이고 이전 값보다 새로운지
- leak_ratio가 0~100 범위인지
- level이 4개 허용값 중 하나인지
- 문자열 길이가 제한을 넘지 않는지


8. TCP 구현 시 반드시 고려할 점
------------------------------

TCP는 패킷이 아니라 연속된 바이트 스트림이다.

한 번의 recv() 결과는 다음 중 어느 것이든 될 수 있다.

- JSON 메시지의 절반
- 정확히 한 메시지
- 여러 메시지가 합쳐진 데이터

잘못된 구현:

data = socket.recv(4096)
message = json.loads(data)

권장 구현:

1. 수신 데이터를 byte buffer에 누적한다.
2. "\n"이 있는지 찾는다.
3. 한 줄만 분리한다.
4. UTF-8 decode와 JSON parse를 수행한다.
5. 남은 데이터는 다음 recv()를 위해 보관한다.

추가 제한:

- 최대 메시지 크기: 예를 들어 4096 bytes
- UTF-8 사용
- 한 메시지 한 줄
- 메시지 안에 임의 줄바꿈 금지
- 알 수 없는 필드는 무시 가능
- 필수 필드 누락 시 거부


9. 전송 주기와 최신 상태 관리
----------------------------

권장 주기:

- Jetson 상태: 5~10Hz
- Jetson Heartbeat: 1Hz
- 단계 변경: 즉시
- Danger ROI 침범: 즉시
- STM32 상태: 2~10Hz
- 일반 로그: 1Hz

Jetson 추론이 30 FPS여도 상태를 30Hz로 모두 전송할 필요는 없다.

네트워크 송신 큐에는 오래된 상태를 계속 쌓지 않는다. 상태 메시지는 최신값만
유지하고, 이벤트와 명령 메시지는 유실되지 않도록 별도의 제한된 큐를 사용한다.


10. 재접속과 통신 장애
---------------------

10.1 Jetson Nano

- Raspberry Pi 연결 실패가 추론을 중단하면 안 된다.
- 통신은 별도 thread 또는 asyncio task로 실행한다.
- 재접속 간격은 1, 2, 4, 8초처럼 증가시킨다.
- 최대 재접속 간격을 약 10초로 제한한다.
- 재연결 후 HELLO와 최신 LeakStatus를 즉시 전송한다.

10.2 Raspberry Pi

- 한 클라이언트 오류로 전체 서버가 종료되면 안 된다.
- 동일 device_id의 중복 연결 정책을 정한다.
- 마지막 메시지 수신 시각을 관리한다.
- 일정 시간 무응답이면 연결을 종료하고 상태를 OFFLINE으로 바꾼다.
- 연결별 송수신 queue 크기를 제한한다.

10.3 STM32

- 상태 수신 주기가 10Hz라면 약 1~2초 미수신 시 COMM_ERROR 후보로 볼 수 있다.
- 통신 타임아웃 시 펌프 정지, 밸브 차단 등 안전 상태로 전환한다.
- 네트워크 복구만으로 DANGER latch를 자동 해제하지 않는다.
- 안전 조건을 확인한 RESET 절차를 사용한다.


11. Raspberry Pi 단일 장애점
---------------------------

현재 구조에서는 Raspberry Pi가 꺼지면 Jetson의 누수 상태가 STM32에 전달되지
않는다. 따라서 STM32의 Fail-safe는 필수다.

안전성이 더 중요하면 다음 보조 경로를 고려한다.

Jetson -> Raspberry Pi TCP: 모니터링, 로그, 원격 제어
Jetson -> STM32 UART: 긴급 누수 및 DANGER 신호
STM32: 최종 안전 FSM과 액추에이터 제어

TCP만 사용한다면 Raspberry Pi 장애와 네트워크 단절 시험을 반드시 수행한다.


12. 네트워크 및 보안
-------------------

- Raspberry Pi에 고정 IP 또는 DHCP 예약 사용
- 설정 파일에 서버 IP와 port 저장
- 장치별 device_id 부여
- 프로토콜 버전 필드 사용
- Raspberry Pi 서버를 인터넷에 직접 노출하지 않음
- 허용된 명령만 처리
- 수치와 문자열 범위 검사
- 최대 메시지 크기 제한
- 필요하면 장치별 공유 token 또는 HMAC 추가
- Raspberry Pi 서버를 systemd 서비스로 등록
- Jetson 클라이언트도 systemd 서비스로 등록


13. STM32 네트워크 방식 확인 사항
--------------------------------

STM32 측 구현 전에 다음 중 어떤 방식인지 확정해야 한다.

- STM32 내장 Ethernet + lwIP
- W5500 Ethernet 모듈
- ESP32/ESP8266 Wi-Fi 모듈
- 다른 TCP/IP 모듈

이 선택에 따라 socket API, 재접속 처리, 수신 buffer와 thread/task 구조가
달라진다.

17. 최종 권장안
--------------

Jetson Nano와 Raspberry Pi는 Python 3을 사용한다.
Jetson -> Raspberry Pi 구간은 NDJSON을 사용한다.
Raspberry Pi -> STM32 구간은 현재 개발 중인 ASCII/CSV 프로토콜을 유지한다.
STM32 코드는 C를 그대로 사용한다.

Raspberry Pi가 NDJSON과 ASCII 사이를 변환하면 각 장치에 가장 적합한 방식으로
통신할 수 있고 STM32의 기존 작업도 보존할 수 있다.

가장 먼저 구현할 항목은 Raspberry Pi asyncio 서버, Jetson 가짜 클라이언트,
STM32 가짜 클라이언트와 프로토콜 단위 테스트다.
